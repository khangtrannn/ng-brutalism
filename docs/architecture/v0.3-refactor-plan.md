# v0.3 Architecture Plan — Decisions from 2026-06-06 Grill Session

> **Status:** Track 1 complete (2026-06-06). Track 2 (NbTabs) next.
> **Context:** Grilling session before adding v0.3 building blocks (Tabs, Signal
> Forms demo, form visual improvements). All decisions below are final unless
> explicitly revisited.

---

## 1. What triggered this session

v0.2.0 shipped. Before adding new building blocks, we audited whether the
library architecture and public API are heading in the right direction — so
v0.3 work builds on a solid foundation rather than compounding existing
inconsistencies.

---

## 2. Architecture direction — confirmed correct

The five-layer capability system
(`tokens → DI tokens → capabilities → primitives → CSS`) is the right
architecture. No redesign needed.

The public API composition model is also correct: **pure composition**
(Fix B). Primitives stay single-responsibility. Verbosity at the template
level is an accepted tradeoff of the model — recipe components in docs absorb
it for common patterns. Consumers who need custom layouts use the primitives
directly.

> **Why Fix B over Fix A (convenience inputs):** Adding typography inputs
> back to Button (or structural inputs to any primitive) is a one-way door.
> It collapses the single-responsibility line that makes each primitive
> predictable. The RxJS analogy holds: each directive/component is one
> operator — clean on the outside, composable with others.

---

## 3. Icon API — accepted as-is

`NbIcon` uses `src` (URL string). No `@ng-brutalism/icons` package is
planned in the near term. The `src` pattern is the long-term API, not a
temporary compromise.

**Implication:** document `NbIcon` explicitly as "bring your own icon
source." Do not attempt to make it declarative (name-based) until the icons
package exists.

---

## 4. Signal Forms — demo/recipe only (Option A)

`NbInput`, `NbCheckbox`, `NbSelect`, `NbTextarea` are **visual shells on
native elements**. They do not and will not implement `ControlValueAccessor`
or any Signal Forms binding.

Signal Forms "just works" with native elements — which means it already works
with `<input nbInput>`, `<select nbSelect>`, etc. without any library changes.

**The plan:** build a docs recipe/demo showing Signal Forms bound to
ng-brutalism-styled native form elements. This is a marketing/community
reference for Angular v22 Signal Forms adoption. No library API changes
required.

---

## 5. Tabs — primitive model (not Angular Material style)

Angular Material's `MatTabGroup` renders the tab strip internally. This
approach was evaluated and rejected for ng-brutalism because:

1. Generated DOM blocks capability composition — consumers can't put
   `nbButton`, `nbChip`, or `nbSurface` on tab triggers.
2. Customisation regresses to CSS overrides instead of design tokens.
3. The parent needs to tunnel capability inputs (tone, radius, shadow, border)
   into its generated DOM — rebuilding what the capability system already
   provides.
4. It creates a split personality: every other component is "consumer authors
   every element"; Tabs would be the one exception.
5. Internal complexity (ContentChildren, QueryList, InkBar) that the
   maintainer owns forever.

**Decision:** Tabs follows the same pattern as the Accordion — **primitive
model with injection token context**:

```html
<!-- Library primitives — maximum flexibility -->
<nb-tabs [value]="activeTab">
  <div nbTabList>
    <button nbTabTrigger value="flights" nbButton tone="surface">Flights</button>
    <button nbTabTrigger value="hotels" nbButton tone="surface">Hotels</button>
  </div>
  <div nbTabPanel value="flights">...</div>
  <div nbTabPanel value="hotels">...</div>
</nb-tabs>
```

- `NbTabs` — manages `activeTab` signal, exposes state via injection token
- `NbTabList` — ARIA `role="tablist"` wrapper
- `NbTabTrigger` — injects context, sets `data-state="active|inactive"`,
  consumer styles it with any primitive
- `NbTabPanel` — injects context, shows/hides based on active state

Active indicator = `[data-state="active"]` CSS selector. No ink bar. No
generated DOM.

```html
<!-- Docs recipe — convenience wrapper for common case -->
<recipe-tab-group [tabs]="tabs" [(value)]="activeTab">
  ...
</recipe-tab-group>
```

The recipe ships in docs, not in the library. Consumers copy it and own it.

## 6. Interactive component seam — confirmed pattern

The accordion already establishes the correct seam for stateful components:

| Layer | Responsibility | Pattern |
|---|---|---|
| Semantic capabilities + scalar transforms | Tone/state plus scalar visual tokens (radius/shadow/border) | `hostDirectives`, input transforms, and CSS vars |
| Injection token | State sharing between parent and children | `InjectionToken<Controller>` |
| `data-state` | Behavior-driven visual changes | `[attr.data-state]` → CSS |

This seam applies to all v0.3 interactive components (Tabs, Dropdown, Drawer,
Switch, RadioGroup). Capabilities handle "what it looks like at rest";
`data-state` handles "what it looks like when active/open/checked."

## 7. Refactor scope — two tracks

### Track 1 — Capability gap (completed)

Six component areas had visual properties but had not adopted the capability
architecture. They created inconsistency visible to consumers — for example,
`NbAccordionTrigger` hardcoded `--nb-main` and ignored the parent item's
`tone` input.

| Component | Problem | Fix |
|---|---|---|
| `NbAccordionTrigger` | Hardcoded `--nb-main`; did not respond to parent/item tone | Adopted `NbToneCapability` and trigger-specific CSS variables |
| `NbProgress` | Had `tone` input, resolved manually via local map | Adopted `NbToneCapability` |
| `NbSticker` | Had `tone` input, resolved via direct tone tokens | Adopted `NbToneCapability` |
| `NbRating` | Had `tone` input, manual resolution | Adopted `NbToneCapability` |
| `NbInput` / `NbTextarea` | Had visual styling, no capability adoption | Adopted `data-nb-tone` plus scalar CSS-variable inputs |
| `NbCheckbox` / `NbSelect` | Had visual styling, no capability adoption | Adopted `data-nb-tone` plus scalar CSS-variable inputs |

**Priority:** Track 1 before any v0.3 work. A fully consistent library is the
foundation; introducing stateful complexity on top of inconsistency compounds
debt.

### Track 2 — Interactive component pattern (design now, build after Track 1)

Tabs is the first v0.3 component to build. The pattern is decided (§5 above).
Design the `NbTabs` API on paper in parallel with Track 1; do not write code
until Track 1 is complete.

---

## 8. What is NOT changing

- Capability system architecture — stays exactly as-is
- Public API naming (tone/radius/shadow/border/gap/padding/separator) — locked
- `NbChipGroup` context broadcasting via CSS variables — stays
- `NbButton` composition model (nbText for typography, nbButtonTrailingIcon
  for trailing icons) — stays
- Recipe approach: docs ship example compositions; library ships only
  primitives

---

## 9. Open questions (deferred)

These were identified but explicitly deferred — do not address in the v0.3
refactor unless a blocking reason emerges:

- `NbPressCapability` — Button/IconButton hover-translate stays local
- `NbFocusCapability` / `NbDisabledCapability` — a11y chapter, post-Track 1
- Shell defaults flip (`radius: xl / shadow: hard / border: strong`) — verify
  against reference designs before changing live defaults
- Surface `size` reconsideration (square dimensions vs Tailwind `size-*`)
- Angular v22 upgrade — prerequisite for Signal Forms demo but independent of
  Track 1
